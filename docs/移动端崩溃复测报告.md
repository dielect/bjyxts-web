# 移动端崩溃复测报告：WASM 内存棘轮与 SystemStackError（2026-10-04）

基线提交：`621cb4e`（含 `da06137`「修复 iOS Canvas 内存峰值及 NPC Viewport 泄漏」与诊断日志模块）。
上一轮排查：[ios-crash-investigation.txt](ios-crash-investigation.txt)（Canvas 像素预算方向，三个问题已修复）。

本轮在 Canvas 修复**之后**的构建上复测，结论先行：

1. **Canvas 修复有效**：静置时登记位图从 12–51 个波动收敛为恒定 10 个；
2. **WASM 线性内存仍以固定速率增长**（静置 ~2 MB/min、正常交互 ~14 MB/min），
   根因不在本项目代码，而在 ruby.wasm 的 JS 桥接层（每帧 await 周期泄漏约 800B 原生内存）；
   这与 Canvas 内存是两个不同的内存域，Canvas 修复无法覆盖；
3. **SystemStackError 依旧必现**：走动 + Enter/Esc 交互约 1–2 分钟内在同一帧位（~4250 帧）崩溃，
   溢出发生在 asyncify/VM 的 C 层，不是游戏脚本里的 Ruby 级递归。

iOS 上「页面崩溃、自动重载」的主凶是第 2 条：60 MB 基线 + 14 MB/min，
玩 20–40 分钟进入 300–500 MB 区间，超过 WKWebView 网页进程的 jetsam 上限即被系统杀掉。
这与开发指南里记录过的 620 MB 协程栈池被杀是同一类死法，只是这次的泄漏源更隐蔽。

## 测量方法

- Linux + 无头 Chromium（playwright 驱动，844×390 触屏上下文），服务 `public/`；
- 复用新上线的诊断口径：WASM 线性内存读 `__vm.instance.exports.memory.buffer.byteLength`
  （与 `diagnostics.js` 的 `wasmBytes` 同源），位图数读 `RG.bmps.size`；
- 插桩版（仅在本地实验用，未入库）：在 `Graphics.update` 里每 600 帧打印
  `GC.stat` 摘要与 eval 计数，通过控制台采集；
- 三种玩法工况：静置（进地图后不输入）、纯方向键走动、完整随机输入（走动 + Enter/Esc）。

## 二、WASM 线性内存棘轮（未解决，主凶）

### 复测数据（修复后构建）

| 场景 | 增长速率 | 备注 |
|---|---|---|
| 静置地图 | **~2.0 MB/min** | 59.2 → 67.1 MB / 240 s，不收敛 |
| 纯方向键走动 | ~2.3 MB/min | 173 s 存活，无崩溃 |
| 完整随机输入 | **~14 MB/min** | 60.4 → 79.9 MB / 114 s，随后触发 SystemStackError |
| 建角界面等待输入 | ~0 | 帧循环停住时零增长（对照） |

注：活跃工况的 14 MB/min 与修复前（14.36）完全一致——Canvas 修复对 wasm 内存无影响，
符合预期（两者是不同内存域）。

### 排除过程（修复前构建上的插桩 + 分块开关实验）

| 实验 | 泄漏速率 | 结论 |
|---|---|---|
| Ruby GC 堆全程 | ~40 页（<1 MB）、存活对象稳定 | 不是 Ruby 对象/字符串泄漏 |
| 每帧 eval 计数 | 77 次 / 4200 帧 | 排除公共事件 eval 编译假设 |
| 显示列表换成 `'[]'`（nolist） | 1.62 MB/min（不变） | 排除每帧 3–4 KB 大字符串序列化 |
| 禁用 Input.update 的 JS 调用（nokeys） | 1.08 MB/min（略降） | 输入调用不是主因 |
| 逐块禁用 Game_Map / Interpreter / Game_Player / Game_Event / Spriteset 的 update | 全部 1.3–2.0 MB/min | 排除游戏逻辑 |
| 每帧 1 次 vs 21 次 JS 调用（spam） | 2.12 vs 2.04 MB/min | 排除按调用次数计费 |
| 每帧只剩一次 `await_js(:frame, '[]', fps)`（both） | **2.12 MB/min** | 泄漏随帧循环本身存在 |

最后一行是定位关键：把每帧逻辑砍到只剩**一次带空参数的 await**，泄漏依然存在且速率相同。
结合「按调用次数无关」的数据，结论是：

> **泄漏源是 ruby.wasm 的 JS 桥接/asyncify 机制在每个 await 周期（每帧一次）固定泄漏约 800B 原生内存；
> 游戏侧交互（对话、菜单、事件解释器）会加深 await 嵌套，泄漏随之放大到 12–16 MB/min。**

两个加重因素：
- 本仓库的 `ruby.wasm` 声明线性内存时**未设上限**（初始 20.9 MB，无 maximum）；
- wasm memory 只增不减，dlmalloc 归还的页也不会收缩 `memory.buffer`，内存压力下无从缓解。

本项目 Ruby/JS 代码基本无责。建议向 [ruby/ruby.wasm](https://github.com/ruby/ruby.wasm) 提 issue：
用 `memory.buffer.byteLength` 按 40 fps 采样跑一个「每帧一次空 await」的最小循环即可复现。

### 建议（按性价比排序）

1. **JS 侧监控 + 自动存档重载（止血，建议先做）**：`diagnostics.js` 已经每 5 秒记录 `wasmBytes`，
   补一个阈值判断（如 350–400 MB）：达到阈值时先让 Ruby 端执行一次内存档
   （复用现有 `persist`/`save_data` 链路），然后 `location.reload()`。
   把「iOS 强杀页面」变成「无感续玩」——读档逻辑本来就会从 localStorage 恢复 `Gmud.sav`。
2. 跟踪 ruby.wasm 后续版本，桥接泄漏修复后升级验证；
3. `boot.rb` 的兜底 rescue 可以把 `SystemStackError` 与其他错误分开提示（见下）。

## 三、SystemStackError（未解决，游戏级崩溃）

### 复现条件

5/5 次复现（含修复后构建，同一种子同帧位 ~4250 帧，换种子在 40–110 s 内）：
新档进入地图后，**走动 + Enter/Esc 随机输入持续 1–2 分钟**。
纯走动（不开菜单、不对话）与纯静置**永不**触发。战斗开关（`battle_calling` 置空）不能阻止。

### 触发链（事件日志实测）

走到 `EV001`（trigger=1，与主角接触）→ 播放 SE + 传送玩家。实测链路：
地图 2 →（EV001）→ 地图 4 →（EV001）→ 地图 3 →（事件 9）→ 传送地图 15，随后崩溃。

### 定位实验

给以下位置全部包上 `rescue SystemStackError` 捕获网（内层先捕获即可定位）：
`Kernel#eval`、`Interpreter#update/execute_command`、`Scene_Map#update/transfer_player`、
`Game_Map#update`、`Spriteset_Map#update`、`Game_Player#update`、`Window_Message#update`、
`Game_Event#update/start`、`Game_Screen#update`、`Scene_Battle/Scene_Menu#main`、
`RGWeb.call`、`RGWeb.await_js`、`Graphics.update`——**无一捕获**，异常直达 `boot.rb` 的
兜底 `rescue Exception`，且 `e.backtrace` 为空。

> 结论：溢出发生在 asyncify/VM 的 C 层（事件解释器调用栈越深越容易触发），
> 不是游戏脚本里的 Ruby 级递归，游戏侧无法直接修复。
> 它在 iOS 上表现为「运行出错」遮罩而非页面崩溃，但同样让游戏玩不下去。

### 建议

1. `boot.rb` 兜底 rescue 对 `SystemStackError` 单独提示
   「遇到兼容性问题，请从菜单存档后刷新页面继续」，避免死在通用错误遮罩上；
2. 与第二条泄漏合并向 ruby.wasm 提 issue（同为 asyncify 嫌疑，可附本轮触发链）；
3. 长期可选：`Interpreter#execute_command` 分批让出以降低单帧内的解释器栈深，
   需要验证对事件时序的副作用，风险较高，仅在上游无修复时考虑。

## 四、iOS 真机验证建议

本轮数据来自桌面 Chromium，jetsam 行为是推断。真机上建议：

1. 用已上线的诊断日志（设置页「导出诊断日志」）确认崩溃前最后的 `wasmBytes`——
   若已在数百 MB，即坐实第二节（wasm 棘轮）；若低位崩溃且游戏内出现「运行出错」遮罩，
   则偏第三节（SystemStackError）；
2. 区分两种现象：Safari「网页出现问题」自动重载（内存被杀）vs 游戏内「运行出错」遮罩（SystemStackError）；
3. 反馈机型、iOS 版本、崩溃前操作（是否在连续对话/传送/菜单切换）。
