## SystemStackError / iOS 自动刷新 根因（2026-10-04 18:20）
- 用户 iPhone 诊断日志（iOS 26.7, CriOS 154）：一次 SystemStackError 于第 4264 帧（wasm 85MB）；
  另一次会话 25 秒/524 帧、wasm 62MB 无错误记录即中断（疑似进程被杀）。
- 根因：ruby.wasm 3.3/3.4 构建（@ruby/3.4-wasm-wasi 2.10.1）在非根 Fiber（evalAsync 跑游戏的 Fiber）里，
  每次跨 C 的非局部跳转（each{break}、raise/rescue；loop{break}/throw 不受影响）泄漏约 60~75 字节 Fiber 栈。
  游戏菜单/事件/场景切换大量使用这些写法，栈累积到 RUBY_FIBER_MACHINE_STACK_SIZE（默认 256KB）即溢出。
  复现：tools/stack-drift-test.mjs 16384 60000 eachbreak|raise
- 加大栈只推迟：256K 第 4~5 轮、512K 第 7 轮、1M 第 12 轮崩溃（tools/soak.py）。
- @ruby/head-wasm-wasi 2.10.1 已修复（同测试 2 万次通过）。方案：换用 head 构建。
- 另：wasm 深 C 递归会先撞宿主原生栈（RangeError Maximum call stack），iOS 原生栈更小。

- 函数编号来自同包 ruby.debug+stdlib.wasm 的 name 段（与 ruby.wasm 代码一致，17825 个函数，59 个导入）：
  9770 _rb_wasm_setjmp_internal，9773 rb_wasm_try_catch_loop_run，17882 asyncify_stop_rewind，global 0 = __stack_pointer
- 补丁 1（9773）：入口保存 SP 到新局部，stop_rewind 后恢复 → 修复 each{break}

## 18:48 结论更新（重要）
- 3.4.1 打补丁 1+2 后 each{break} 修好，但 raise/rescue 仍在约 224 次（原版 282 次）后 "stack level too deep"，
  且与机器栈/VM 栈大小无关；游戏压力测试补丁版第 3 轮即崩 → 游戏崩溃主因是这一类，补丁 1+2 不够。
- @ruby/4.0-wasm-wasi 2.10.1（ruby 4.0.0，含 zlib 3.2.2）：raise/eachbreak/await/throw 2 万次全过。
  但启动 RSS 423MB。原因：Ruby 4.0 shape.h 中 SHAPE_BUFFER_SIZE = 1<<19（不分平台），
  REDBLACK_CACHE_SIZE = SHAPE_BUFFER_SIZE*32 = 16777216 节点，WASI 的 mmap 用 malloc+清零模拟 → 约 256MB 真实占用。
- 方案：给 4.0 打补丁，Init_default_shapes（调试版 func 7327）里 `i32.const 16777216`（缓存节点数）改 0，
  使 mmap 失败 → 源码自带的退路：shape_cache=0、cache_size=上限，即不用红黑树缓存（只影响深层 ivar 查找速度）。
- 4.0 ruby.wasm：59 个导入，18151 个函数。

## 19:20 iOS 26 自动刷新：WebKit 优化编译器内存暴涨（真正根因）
- 用户日志（iPhone, iOS 26.7, Chrome/CriOS=WebKit）：运行 5～35 秒后会话无 pagehide 中断，下一会话 navigation=back_forward；
  wasm 55MB、画布 7MB、JS 堆 5MB 全正常。Chromium 实测页面进程 RSS 稳定约 280MB，不增长 → iOS 特有。
- WebKit bug 304810 “High memory usage in WASM compilation thread”：https://bugs.webkit.org/show_bug.cgi?id=304810
  复现仓库：https://github.com/frankhinek/webkit-wasm-compiler-memory-repro
  - Asyncify 构建的 wasm，运行几秒后 JSC 的 OMG 编译（JSC::Wasm::OMGPlan::work、Air::allocateRegistersByGreedy）把进程推到数 GiB；
    iPhone 16 Pro / iOS 26.6.2 上 4/4 次被 jetsam per-process-limit 杀掉并自动重载（back_forward）。
  - 绕过：JSC 不对超过 maximumOMGCandidateCost=100,000 字节的函数体做 OMG。把 >40KB 的函数体填充到 160KB
    （locals 后插入 block; br 0; nop×N; end，填充不执行）后 0/3 被杀。只填两个最大的不够，第三个也要填。
  - 另一个绕过（评论区 Walter B.）：wasm-opt 重新跑 --asyncify 加若干优化；对 ruby.wasm 不适用（已 asyncify）。
- ruby.wasm（4.0 补丁版）：18151 个函数体，>100KB 2 个，>30KB 19 个，>40KB 11 个；代码段共 11.7MB。
- 方案：tools/pad_wasm_omg.py 把 >30KB 的函数体填到 110KB，构建时自动执行。
